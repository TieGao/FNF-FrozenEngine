## 一、openfl 的「GPU Caching」到底是什么

**它不是开关，是 `readable = false` + 「被画过一次」的副作用。**

`BitmapData.getTexture(context)`（`BitmapData.hx:2254-2322`）每次绘制时被调用，做三件事：

1. `__texture` 为空 → `createRectangleTexture(w, h, BGRA, false)` 建纹理；
2. `image.version > __textureVersion` → 上传（需要时 clone + premultiply）；
3. `if (!readable && image != null) { __surface = null; image = null; }` ← **唯一丢 CPU 副本的地方**。

所以四种状态：

| 状态 | `image` | `__texture` | `readable` | CPU 占用 | GPU 占用 | 触发条件 |
|---|---|---|---|---|---|---|
| A 纯内存 | 有 | null | true | w·h·4 | 0 | 默认 |
| B 标记不可读 | 有 | null | false | w·h·4 | 0 | `disposeImage()`，但**这一帧没画到** |
| C 双份 | 有 | 有 | true | w·h·4 | w·h·4 | 画过但没 `disposeImage()` |
| D 纯显存 | null | 有 | false | 0 | w·h·4 | `disposeImage()` **且**画过一次 |

推论：
- `disposeImage()` 全文只有一行 `readable = false;`（`:823-826`），**零字节释放**。B 态是最坏状态：白标了却什么都没省。
- 预载了但这一局没画到的图永远停在 B 态 —— 这是 `makeHardwareOnly` 存在的理由。
- `readable=false` 后 `getPixel32` 返回 **0**（`:2190`），`getPixels` 返回 **null**，不崩。以前记的「空引用崩」是错的：后果是**功能静默失效**，不是异常。

### 显存只有一条释放路径

全 openfl 里 `gl.deleteTexture` 只出现 2 次：`BitmapData.hx:801`（**被注释**）和 `TextureBase.hx:96`（唯一生效）。`TextureBase` 也**没有 finalizer**。

⇒ `bmp.__texture.dispose()` 是唯一能真正释放显存的调用。任何走 flixel `destroyOnNoUse` / `clearCache` / `graphic.destroy()` 的销毁都**永久漏纹理**（flixel 全库没有一处 `TextureBase.dispose`）。

⇒ 我们 `destroyGraphic()` 的顺序（先 `__texture.dispose()`，再 `FlxG.bitmap.remove()`）是**必需的**，不能改成「交给 flixel 销毁」。`FlxG.bitmap.remove()` 自身会 `graphic.destroy()` → `bitmap.dispose()`，此时纹理已删，安全。

### 三个连带陷阱

1. **`__texture.dispose()` 之后不会重建**：`getTexture` 判据是 `__texture == null || __textureContext != context.__context`，dispose 只清 `__textureID`，字段还在 → 后续渲染拿到已删句柄 → **永久黑图，不报错**。所以「只在 `useCount<=0` 时销毁」不能放宽。
2. **`clone()` 一个纯显存 BitmapData 会共享 `__texture`**：任一方 dispose，另一方永久黑。更麻烦的是 `FlxGraphic.getBitmap = Unique ? Bitmap.clone() : Bitmap`（`FlxGraphic.hx:230-232`）—— `loadGraphic(..., unique=true)` 的语义是「给我一份能随便改的独立副本」，对 GPU-only 源图这份「副本」共享同一张纹理 → 调用方以为在改副本，实际写穿原图或被静默丢弃。
3. **`fromTexture()` 会先 `new BitmapData(w, h, true, 0)`**（`:1397`）再 `image = null` —— 每转一张图临时分配一份 `w·h·4` 的 CPU buffer。批量转换必须分批 + 批间 GC。

### `full` 模式的兼容性边界（重要）

GPU-only 的图**没有 CPU 像素**，因此任何需要 CPU 像素的 flixel 功能都会失效。逐个确认过行为：

| 调用 | 源为 GPU-only 时 |
|---|---|
| `getPixel32` / `getPixels` | 返回 `0` / `null`（`:2190`, `:2210`） |
| `copyPixels`（`FlxFrame.paint` 走这条） | **静默 no-op**（lime `Image.hx:415` 有 `sourceImage == null` 检查） |
| `draw` / `fillRect` | **无 readable 守卫**，会写进共享纹理（`fillRect` 甚至清空整张纹理） |
| `clone()` | 产出的副本仍共享同一 `__texture` |

受影响的功能（全部是**静默失效，不报错**）：
- `FlxFrame.paint()` → `sprite.framePixels`（`MouseEvent.hx:90-108` 的像素级点击判定全部返回 false）、`FlxGraphic.fromFrame`（抠帧得空白）、`FlxSpriteUtil.alphaMaskFlxSprite`（遮罩全空）。
- `FlxSprite.stamp` / `FlxSpriteUtil.updateSpriteGraphic`（`drawLine/drawRect/fill` 等）—— 写穿共享纹理，会污染同一图集里的其它帧。

⇒ 硬规则：**`gpuCaching=full` 只适用于「纯显示、绝不二次加工」的图**。mod 脚本对角色调 `drawLine/stamp`、像素判定、抠帧这些场景需要 CPU 像素，应在 `full` 下视作不支持（或让这些调用方走 `allowGPU=false`）。`auto` 模式只在首次绘制后丢 CPU，**同样有这个问题**，只是延后发生。

## 二、别人的内存管理（横向）

| 引擎 | 引用计数 | 分代 | 显存释放 | 预载策略 | 降采样 | 预算/LRU | 懒加载 |
|---|---|---|---|---|---|---|---|
| Psych 0.1.1→1.0.4 / EK / Mobile | **无** | 无 | 1.0 起 `__texture.dispose()` | 1.0 起**全量预载**（无上限） | 无 | 无 | 无 |
| NovaFlare | flixel `useCount` | 无 | 交回 flixel（**上游 openfl 会漏**，它用 fork openfl 9.5） | `cacheBitmap(..., false)` 预载不上传 | 无 | 无 | 无 |
| VS Impostor | 无（不看 useCount） | 无 | `disposeImage()` = 只有 B 态 | `cacheBitmap(..., false)` | 无 | 无 | 无 |
| Codename | **代际**（`AssetCache` 层） | ✅ pre/postStateSwitch | `removeByKey` → flixel destroy（**漏纹理**） | 无预载 | 无 | 无 | 无 |
| NightmareVision | flixel `useCount` | 无 | `__texture.dispose()` + `Gc.compact` | 同 Psych | 无 | 无 | 无 |
| **官方 Funkin 0.8.7** | **无**（`FunkinMemory.hx:235` 的 `useCount > 0` 判断写反，整条分支失效） | ✅ 三代 Map | 构建期 ASTC（10x10/4x4） | `preloadLevelAssets()` **函数体被注释掉** | ❌ 运行时无 | 无 | 无 |
| **FE（我们）** | `useCount` + `pendingReleases` | ✅ `trackedEpochs` | `__texture.dispose()` ✅ | 全量 + `pinGraphic`/`pinSound` | 试过，回退 | 无 | 无 |

**三条硬结论：**

1. **降采样 / 显存预算 / 角色懒加载，两条谱系全都没有。** 最接近的只有 Codename 读 VRAM 总量做系统信息展示。Funkin 靠的是**构建期 ASTC 压缩**（改资源文件，不是运行时）。⇒ 8.88GB 压进 6GB 这件事没有先例，必须自研。
2. **「代际 GC」不是我们发明的**：官方 Funkin 的 `FunkinMemory.hx` 就是 permanent/current/previous 三代，purge 时整批销毁 previous、重请求时从 previous 捞回。Codename 也在 `AssetCache` 层做了同样的事。我们的 `trackedEpochs` 与它们同构，方向是对的。
3. **我们比所有 Psych 系都先进**：`pendingReleases`（延迟释放）+ `pinGraphic`（预载保护）+ `trackedEpochs`（代际）这一套，Psych 全系零命中。Psych 1.0.3 的 `freeGraphicsFromMemory()` 靠反射扫 `FlxG.state.members` 当白名单，漏 substate、漏非 graphic 字段引用，**不要抄**。

## 二·六、按显存分档（2026-11-12 17:05 构建）

**问题**：预载是否上传显存，6GB 卡和 12GB 卡应该相反。6GB 卡上传就溢出，12GB 卡上传能省掉进歌的现传卡顿。

**读显存**：openfl 的 `Context3D.totalGPUMemory` 只查 `NVX_gpu_memory_info`（NVIDIA 专有），AMD 上恒为 0。改用 DXGI：

```haxe
// MemoryStats.getDedicatedVideoMemory()（@:functionCode）
IDXGIFactory1* factory = nullptr;
CreateDXGIFactory1(__uuidof(IDXGIFactory1), (void**)&factory);
// 枚举所有适配器，取非软件适配器的 DedicatedVideoMemory 最大值
```

`#pragma comment(lib, "dxgi.lib")`，NVIDIA / AMD / Intel 通用（Win7+）。

**策略**：新设置项 `preloadTextureToVRAM`（Graphics 页，三套菜单都有）：

| 值 | 行为 |
|---|---|
| `auto`（默认） | 独占显存 >= **10GB** 才在预载时上传 |
| `on` | 总是上传（大显存卡，进歌不用现传） |
| `off` | 从不上传（运行时第一次索取才传） |

阈值取 10GB 而不是 8GB：Fatal Finale 这类 mod 预载就有 8.88GB，8GB 卡开了会溢出到系统内存，比按需上传更慢。探测失败（返回 0）时 `auto` 退化为 `off`。

**跨平台行为**（`#if (cpp && windows)` 包住 DXGI 的三处：cppFileCode 的 include、`getDedicatedVideoMemory` 定义、`dedicatedVRAM` 的调用分支）：

| 目标 | DXGI 探测 | `auto` 的实际行为 |
|---|---|---|
| Windows (cpp) | ✅ | 按独占显存判定（≥10GB → on） |
| Linux (cpp) | ❌ 编译期整块排除 | `dedicatedVRAM()` 返回 0 → 退化为 `off` |
| macOS (cpp) | ❌ 同上 | 同上 |
| Android (cpp) | ❌ 同上 | 同上 |
| HTML5 | ❌ 同上 | 同上（这个项目本来也不编 html5：`linc_luajit` 是 native 库） |

**验证方式**：把 `export/release/windows/haxe/release.hxml` 里的 `-D windows` 换成 `-D linux`、`-cpp` 指向临时目录，跑 `haxe <hxml> --no-output` —— **零错误**。这证明「cpp 但非 Windows」这条分支（也就是 linux/mac/android 共用的分支）能正常编译，且没有任何残留的 Windows 类型引用。

`__vramCache` 也包在 `#if (cpp && windows)` 里，非 Windows 上不存在这个字段。

**F9 报告**新增「显卡」段：

```
显卡
  独占显存 12.0GB   // DXGI 查到的总量；探测失败为 0
  预载上传 开       // auto（auto = 显存 >= 10GB）
```

## 三、三个确定的 bug（按性价比排序）

### ✅ ① `optimizeForRenderToTexture` 传错 —— 改 1 个字符（已修）

`Paths.hx:990` 传 `true`，`RectangleTexture.hx:39` 因此执行 `__getGLFramebuffer(true, 0, 0)`，为**每一张图**额外建 FBO + `DEPTH24_STENCIL8` renderbuffer（`renderbufferStorage(w, h)` = 4 B/px）。

在 4 B/px 的纹理之上再叠 4 B/px ≈ **+100% 显存**（报告里按 3 B/px 估 +75%）。8192² 一张就是 256MB 额外。

openfl 自己在 `getTexture():2261` 传的是 `false`；NovaFlare 也传 `true`（同一个旧代码抄来的），所以不是设计取舍。**改 `false`，零风险。**

**但更好的做法是根本别自己建纹理**（见下面的替代方案），那样参数传错的问题自动消失。

### ✅ ② 预载默认走 GPU —— 改 1 行（已修）

`LoadingState.hx:521` → `Paths.cacheBitmap(key, bitmap)`，`allowGPU` 用默认 **true**。
于是 `gpuCaching == full` 时预载阶段就把全部 185 张图上传显存（再叠上 ① 的 +100%）。

NovaFlare / Impostor 都是 `cacheBitmap(..., false)`：**预载只解码，运行时第一次索取才上传**。我们 `image()` 命中分支已写好这个逻辑（`Paths.hx:1027-1029`），只差把预载这一侧的 `allowGPU` 关掉。

### ✅ ③ `makeHardwareOnly` 应改成「让 openfl 自己丢」（已修）

现在的实现是 `createRectangleTexture` → `uploadFromBitmapData` → `BitmapData.fromTexture`，代价：
- 自己建纹理（踩 ① 的 FBO 坑）；
- `fromTexture` 内部先 `new BitmapData(w, h, true, 0)` 再丢弃（`w·h·4` 临时 buffer）；
- 产出的 BitmapData 与任何 clone 共享 `__texture`，所有权语义脆弱。

**更好的写法（等价于 NovaFlare fork 的 `disposeOnUpload`，但不用改库）：**

```haxe
static function makeHardwareOnly(bitmap:BitmapData):BitmapData
{
    if (bitmap == null || bitmap.image == null) return bitmap;
    try
    {
        var stage = FlxG.stage;
        var context = (stage != null) ? stage.context3D : null;
        if (context != null)
        {
            bitmap.disposeImage();          // 只置 readable = false
            bitmap.getTexture(context);     // openfl 自己建纹理(BGRA,false) + premultiply 上传
                                            // 末尾的 !readable 分支会自己把 image 置 null
        }
    }
    catch (e:Dynamic) {}
    return bitmap;
}
```

一次 `getTexture` 就把「建纹理 + premultiply 上传 + 丢 CPU」全做完了，走的是 openfl 自己的代码路径：
- 参数永远正确（内部传 `false`）；
- 没有 `fromTexture` 的临时分配；
- 没有「两个 BitmapData 共享一个纹理」的所有权问题；
- 失败时最坏退化成 B 态（`readable=false` + image 还在），不影响正确性，只是没省内存。

NovaFlare 那个 fork 只是在 `getTexture()` 上传后加了一句 `if (disposeOnUpload) readable = false;`（fork `:2317`），语义与上面这段完全等价 —— 说明这个方向是被验证过的。

### ③ `fromTexture` 的临时 CPU buffer —— 分批

见 §一.3。`full` 模式批量转换时，每张图都有一次 `w·h·4` 的瞬时分配。

## 四、Fatal Finale 8.88GB 的完整成因链

1. **Psych 1.0 引入的全量预载**（`1.0.4-OG/LoadingState.hx:798`）：工作线程把 preload JSON 里每一张图整张 `BitmapData.fromFile()` 解码进 `requestedBitmaps`，主线程 `:341-351` 统一 `cacheBitmap()`。**`loadMax` 就是全部，无上限、无分帧。** 0.7.3 根本不预载图片 —— 这是 1.0 的回归。
2. 峰值 = **全部 CPU 位图 + 全部 GPU 纹理同时存在**（C 态，见 §一）。
3. 叠加 ① 的 +100% 显存 → 6GB 卡溢出 → WDDM 在系统内存再留一份 → RSS 冲到 15.3GB。

修 ① ② 之后，峰值应该回到「CPU 全量 + 只上传真正画到的图」，这才是正常量级。

## 七、可抄的四条（外部先例）

1. **`forceRender()`**（Funkin `FunkinMemory.hx:254-267`）：预载后强制上传一次 GPU，避免进游戏首帧卡顿。我们 `full` 模式已经是这个思路。
2. **permanent 白名单 + 自动注册**（Funkin `FunkinMemory.hx:31-93`）：用 `Assets.list()` 把所有 `ui/*.png` 注册为常驻，免得每代都被扫描。我们有 `dumpExclusions`，但靠手写。
3. **`cpp.NativeGc.run(true)`**（Psych Mobile `Paths.hx:54-56`）：major GC 才把 hxcpp 大对象还给系统 —— 比 `System.gc()` + `Gc.compact()` 更直接，可加入 `frequentGC` 分支。
4. **`MemoryUtil.getTaskMemory()`**（官方 `util/MemoryUtil.hx:70`）：Windows 工作集 / Linux VmRSS，可作为「显存近似仪表」。我们的 F9 已经在读 RSS，可以补 VRAM 估算。
