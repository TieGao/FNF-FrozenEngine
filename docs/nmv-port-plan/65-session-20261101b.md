## 1. **多人唱机制：确认是 `note.lane`（= player），不是 `mustHitSection`**

### 1.1 NMV 的做法（源码取证）

| 位置 | 事实 |
|---|---|
| `Song.hx:29` | `var player2:String;` —— 只有 `player1/player2/player4`，**`player4` 全仓零引用**（遗留字段） |
| `PlayState.hx:905` `generatePlayfields()` | `for (lane in 0...SONG.lanes)`；`character = (lane == 1 ? dad : boyfriend)`；`isPlayer = (lane != 1)`；`auto = (lane != 0 \|\| cpuControlled)` |
| `Note.hx:403` | `player = lane = queueNote.playField;` |
| `ChartEditorState.hx:2310` | `note.lane = Math.max(Math.floor(intendedData / song.keys), 0);` |
| `ModManager.getCenterX(lane, keys)` | lane 0 贴右（玩家）、lane 1 贴左（对手）、**lane >= 2 屏幕正中** |

**结论：谱面的 `sectionNotes[1]` 是「绝对车道」`0 .. lanes*keys-1`；**
- `lane = noteData / keys`（整除）→ 哪条 playfield
- `column = noteData % keys` → 该 field 内的列（`note.noteData`）

`monotone-attack`：`lanes=4, keys=4` → 16 条车道：
| 车道 | lane | 角色 | 是否玩家可玩 |
|---|---|---|---|
| 0-3 | 0 | boyfriend | **是**（唯一可操作） |
| 4-7 | 1 | dad | 否（auto） |
| 8-11 | 2 | boyfriend | 否（auto） |
| 12-15 | 3 | boyfriend | 否（auto） |

所以它**视觉上只有两个角色**（bf / dad），但有 **4 条 strumline**，bf 一个人 auto 唱另外两条。
用户看到"白 note 本应 2 人分着唱、结果全被 dad 唱"= 移植端把 8-15 折回 0-7 后，
8-11 落回 bf 侧、12-15 落进 dad 侧；而 `mustPress` 仍由 section 的 `mustHitSection`（只有两态）决定。

### 1.2 移植端现状与差距

已有：`Note.player`（NMV 脚本面）、`Note.nmvLane`（引擎内部，`PlayState:2555` 逐 note 写入）、
`ModManagerCompat.getCenterX/getStrumX`（P0，64 号加的）。

缺的是三件事：
1. `PlayState` 不读 `SONG.lanes`（`keys = isCoopMode() ? 8 : 4` 写死），`generateStaticArrows`
   只生成 2 组 × keys 条；
2. note 生成时 `nmvLane` 记的是绝对车道，但**没有拆成 `lane` + `column`**，`mustPress`
   走 section 的 `mustHitSection`；
3. 没有"lane >= 2 居中"的 strum 布局。

### 1.3 实施清单（下一轮直接照这个做）

```haxe
// ① PlayState：读谱面 lane 数（默认 1 == 现有两轨布局，完全不影响老歌）
final lanes:Int = (Reflect.field(SONG, 'lanes') is Int) ? Std.int(Reflect.field(SONG, 'lanes')) : 1;

// ② note 生成：绝对车道 → (lane, column)
final absData = Std.int(noteData);
final lane    = Std.int(absData / keys);
final column  = absData % keys;
swagNote.nmvLane  = absData;
swagNote.player   = lane;                      // NMV 语义
swagNote.mustPress = (lane == 0);              // 只有 lane 0 可操作（NMV auto = lane != 0）

// ③ strum 生成：lanes > 1 时走新分支，1 时保持现状
for (lane in 0...lanes) for (col in 0...keys) {
    final s = new StrumNote(0, 0, col, (lane == 0) ? 1 : 0);
    s.x = ModManagerCompat.getCenterX(lane, keys) + ModManagerCompat.getStrumX(col, keys);
    // 注意：不要调 s.playerPosition()，它按 player 加半屏偏移，会把居中 lane 推走
}
```

**风险点（务必先处理）**：
- `StrumNote.playerPosition()` 必须跳过，否则 lane 2/3 被推回左右半屏；
- `playerStrums` / `opponentStrums` 两个子组容纳不下 4 组 → lane >= 2 要单独成组
  （或全部塞 `strumLineNotes`，判活只看 `note.mustPress`）；
- 输入映射只绑 lane 0，`opponentStrums` 的 `cpuSide` 逻辑（`strumGroupIsCpuSide`）要按 lane 判；
- splash 预热数量 `getColumnsPerPlayer(SONG)` 要跟着变成 `lanes * keys`。

## 2. Danger Black 变身失败 = **Character 没有 `animSuffix` 字段**

### 2.1 变身链

- 角色：`data/characters/danger.json`，`image = characters/story/black/danger`（**Animate 图集**）
- 动画里有成对的 mad 变体：`idle` / `idle-mad`、`singUP` / `singUP-mad` …（共 5 组）
- 触发（`data/stages/danger.hx:215`）：
  ```haxe
  case 'scream danger':    dad.playAnim('scream2', true); dad.animSuffix = '-mad';
  case 'unscream danger':  dadLegs.playAnim('legs-mad', true);
  ```
- NMV 的落点（`funkin/objects/Character.hx:357`）：
  ```haxe
  override function playAnim(animToPlay, isForced, isReversed, frame) {
      animToPlay += animSuffix;   // ← 变身就靠这一行
      super.playAnim(animToPlay, ...);
  }
  ```

### 2.2 移植端缺陷

`Character` **完全没有 `animSuffix` 字段**（`grep` 零命中）→ hscript 的
`dad.animSuffix = '-mad'` 被静默丢弃 → 之后所有 `playAnim('idle')` 还是 `idle`
→ 角色不变身。

### 2.3 改动（`source/objects/Character.hx`）

1. 新增 `public var animSuffix:String = '';`
2. `playAnim` 开头拼后缀，**但先查一次 `hasAnimation(名字+后缀)`**，缺变体就退回原名
   （NMV 是直接拼、拼不到拉倒；这里加一层保护，避免某个动画没有 mad 版时整条动画空掉）。
3. 后续所有 `AnimName` 用法（`atlas.anim.play` / `animFlipXMap` / `animOffsets` /
   `nmvApplyOffset`）改用拼好的 `target`。

## 4. maroon 漂移：上一轮那个 scale 改动是**错的，已回退**

### 4.1 用 openfl 源码证伪

```haxe
// openfl 9.5.2 src/openfl/geom/Matrix.hx:743
public function translate(dx:Float, dy:Float):Void {
    tx += dx;        // ← 纯加！不乘 a/d
    ty += dy;
}
// :620  scale 才是右乘
public function scale(sx:Float, sy:Float):Void { a *= sx; b *= sy; ... }
```

所以参考引擎 `drawAnimate` 里的 `matrix.translate(-bounds.x, -bounds.y)` 落在**世界空间**，
与角色 `scale` **无关**（62 号的原判断是对的）。我 10-31 深夜按"translate 是右乘"
推导成"符号空间、要乘 scale"，是错的 —— 已回退成 `offset = json偏移 + bounds`。

### 4.2 真正的漂移原因仍待一条日志

`nmv off` 面包屑加了两个决定性字段：

```
nmv off maroonthreat <anim> flip=<bool> scale=<sx,sy> bw=<w> bh=<h> json=<jx,jy>
        anchor=<ax,ay> -> <ox,oy> origin=<ox,oy> fw=<fw>,<fh>
```

- **`origin`**：`drawLimb` 是按 `(p - origin) * scale + origin` 缩放的，
  origin 不为 0 且 scale ≠ 1 时，画面整体偏 `origin * (1 - scale)`。
  maroonthreat scale=0.9、若 origin 是 (365, 300) 之类 → 偏 36/30 像素，**每个动画都偏**。
- **`fw/fh`**：flxanimate 的绘制尺寸，用来判断 `NmvAtlasAnchor` 算出的 bounds 与真实内容是否错位。

拿到这行就能判死：origin 非 0 → 在 `copyAtlasValues` 前把 nmv 角色的 origin 归零；
bounds 与 fw/fh 明显不等 → 换 `NmvAtlasAnchor` 的遍历口径。
